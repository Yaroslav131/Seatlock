# ADR 0007. Gateway: список публичных маршрутов, лимит частоты, таймауты, кеш, агрегация и две реплики

- **Статус:** принято
- **Дата:** 2026-09-21

## Контекст

До этого gateway был «трубой»: пять `createProxyMiddleware` с `pathFilter` по префиксу. Что из этого
следовало (нагрузочное тестирование, сентябрь 2026):

- наружу был виден **любой** путь под `/api/auth`, `/api/catalog`, `/api/booking`, `/api/payment`,
  включая внутренние (например, `ticket-info` каталога, который нужен только `payment`);
- лимит частоты был только у `auth` (in-memory, отдельно на каждый процесс), в README он ошибочно
  приписывался gateway; остальные пути не ограничивались вообще;
- таймаутов не было: зависший сервис держал соединения клиента до бесконечности;
- карта мест каждые 7 секунд делала три запроса (занятые, проданные, свой холд), и все они
  шли до сервисов, сколько бы зрителей ни смотрело одно событие;
- на сервере одна копия gateway, деплой её перезапускал, и в эти секунды сайт не отвечал.

## Решение

**1. Список публичных маршрутов** (`src/proxy/routes.ts`) — единственный источник правды: метод, путь,
политика лимита, признак «без таймаута», признак «кешируется». Путь под префиксом сервиса, которого нет
в списке, получает 404 на самом gateway (метрика `gateway_route_blocked_total`). Закодированные слэши
(`%2f`), `..` и завершающий слэш нормализуются или отклоняются. Swagger сервисов оставлен публичным (это
заявленная возможность). Новый эндпоинт сервиса не становится публичным, пока его явно не запишут сюда.

**2. Таймауты только там, где деньги ещё не тронуты.** Ответ сервиса ждём `UPSTREAM_TIMEOUT_MS`
(15 с): 504, если завис; 502, если недоступен. **Без таймаута** возврат денег
(`PATCH /orders/:id/refund`), вебхук платёжного провайдера и demo-вебхук: если оборвать такой запрос
после того, как провайдер уже списал деньги, клиент увидит ошибку при прошедшем платеже. Пусть лучше
запрос виснет, чем деньги и заказ разойдутся. Создание заказа таймаут имеет: деньги на этом шаге ещё
не списаны, а повторный запрос идемпотентен (создание заказа возвращает уже существующий активный заказ).

**3. Лимит частоты на Redis** (`src/rate-limit/`), по IP, фиксированное окно (одна Lua-команда:
`INCR` и `PEXPIRE` атомарно). Политики: вход и регистрация 20/мин, заказ 30/мин, занятие места 60/мин,
остальное 600/мин; **вебхук провайдера не ограничивается**. Счётчики общие для всех реплик. Если Redis
недоступен или молчит дольше 100 мс, запрос **пропускается** (fail-open, метрика
`gateway_rate_limit_errors_total`): лимит защищает сервис, и падение Redis не должно ронять сайт.
IP берётся из `X-Forwarded-For` с учётом `TRUST_PROXY_HOPS` (в проде 1, Caddy): доверять любой записи
означало бы дать клиенту подделать адрес и обойти лимит. Для нагрузочных тестов с одного адреса есть
`RATE_LIMIT_BYPASS_IPS` и `RATE_LIMIT_ENABLED`. Собственный лимит `auth` (5/мин на вход и на
регистрацию) остаётся: он строже и работает независимо.

Ограничения: окно фиксированное, на стыке окон возможен всплеск до 2N; лимит по IP бьёт по нескольким
людям за одним NAT (значения выбраны с запасом для человека в браузере).

**4. Кеш публичных GET каталога** на 5 с в памяти реплики с объединением одинаковых запросов
(`src/cache/ttl-cache.ts`): когда запись протухла, а зрителей много, к каталогу уходит один запрос,
остальные ждут его. Кешируются только ответы 200 на запросы без токена и cookie (иначе ответ мог бы
оказаться персональным). Каталог уже кеширует в Redis, поэтому выигрыш здесь в CPU каталога и одном сетевом
хопе под всплеском, а не в базе. Задержка видимости изменений до 5 с (публикация события, генерация мест).

**5. Агрегация `GET /api/events/:id/seat-status`.** Занятые (booking), проданные (payment) и, с токеном,
свой холд одним ответом; фронтенд вместо трёх запросов делает один. Публичная часть кешируется на 1 с с
объединением запросов, поэтому нагрузка на booking и payment не растёт вместе с числом зрителей события.
Свой холд не кешируется. После собственного действия (занял, отпустил) фронтенд просит `?fresh=1`
(учитывается только с токеном), иначе отпущенное место до следующего опроса показывалось бы «занятым».
Старые эндпоинты остаются для уже открытых вкладок.

**6. Сквозной `x-request-id`**: принимается безопасный клиентский (8–64 символа `[A-Za-z0-9._-]`), иначе
выдаётся UUID; возвращается клиенту и передаётся сервисам.

**7. Две реплики за Caddy.** `gateway` и `gateway-2` (`least_conn`, активная проверка `/health` раз в
5 секунд, пассивная пометка после первой ошибки). CD обновляет реплики по очереди и ждёт, пока новая
станет healthy. Конфигурацию проверили на заглушках: остановка одной реплики под потоком запросов
давала 2 из 60 ответов 502, причина не в обрыве соединения, а в том, что запросы к остановленной реплике
ждали весь `lb_try_duration` в попытке соединения; `dial_timeout 1s` и `max_fails 1` дали 0 ошибок из 60
в трёх прогонах. Повтор на другой реплике: любой запрос, если соединение не установлено (запрос не ушёл),
и только GET/HEAD, если оно оборвалось посреди запроса. Заказ или возврат не выполнятся дважды.

Вторая реплика **не добавляет пропускной способности**: на сервере два ядра, и все сервисы делят их
между собой. Её смысл в доступности при деплое и сбое процесса.

## Последствия

- Явный список маршрутов надо поддерживать: новый публичный эндпоинт сервиса без строки в
  `routes.ts` вернёт 404 (тесты в `routes.spec.ts` и интеграционный тест ловят это на CI).
- Клиенты с одного IP при превышении получают 429 с `Retry-After`; нагрузочные тесты обязаны
  использовать обход (см. `packages/load-test/README.md`).
- Кеш у каждой реплики свой: одно и то же событие в пределах TTL может одну секунду отличаться между
  репликами.
- Новые метрики: `gateway_route_blocked_total`, `gateway_rate_limited_total`,
  `gateway_rate_limit_errors_total`, `gateway_cache_total{result}`, `gateway_upstream_errors_total{service,kind}`.
- Kubernetes (следующий этап) заменит связку Caddy + две реплики на Service/Ingress; список маршрутов,
  лимит на общем Redis и таймауты от этого не зависят.
