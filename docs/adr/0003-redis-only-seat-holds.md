# ADR 0003. Холды мест хранятся только в Redis, без Postgres

- **Статус:** принято
- **Дата:** 2026-09-08

## Контекст

Сервису `booking` нужно временно "запирать" место за пользователем на время
выбора (по умолчанию 5 минут), с автоматическим освобождением по таймауту
и атомарной защитой от гонки двух пользователей за одно и то же место.
Постоянного состояния "куплено/оплачено" в этой итерации ещё нет — оплата
(Stripe) намеренно вынесена в отдельную, более позднюю фазу.

## Решение

`booking` не заводит Prisma-схему и Postgres-таблицу вообще. Источник
истины для холда — три ключа в Redis с TTL:

- `hold:{eventId}:{seatId}` = `userId` — авторитетно "занято/кем".
- `user-hold:{userId}:{eventId}` = `seatId` — активный холд юзера в
  этом событии (восстановление после reload, правило "один холд на
  событие на юзера").
- `event-holds:{eventId}` — ZSET-индекс (member=seatId, score=expiry в мс)
  для дешёвого листинга занятых мест без `KEYS`/`SCAN`.

Атомарность (перенос холда, отказ при гонке) — два Lua-скрипта через
`redis.defineCommand`, а не Postgres-транзакция с блокировкой строки.

## Почему не Postgres

- Данные по дизайну живут единицы минут — ничего не теряется даже при
  полной потере состояния Redis, а Redis в проде и так персистентен
  (`--appendonly yes` в `docker-compose.prod.yml`), реального риска
  потери нет вовсе.
- Атомарность check-and-set всё равно нужна независимо от хранилища —
  Postgres потребовал бы `SELECT ... FOR UPDATE` ровно за тем же, просто
  на другом движке. Держать оба хранилища значило бы решать классическую
  проблему двойной записи (dual write) — что делать, если Redis-SET
  прошёл, а Postgres-INSERT упал, или наоборот — ради нулевой выгоды:
  сейчас ничто ниже по стеку не читает историю холдов.
- Схема постоянной записи (`Order`/`Booking`) реально прояснится только
  вместе с дизайном оплаты — заводить её раньше означало бы гадать.

## Когда пересмотреть

Как только в проект добавляется оплата — тогда `booking` получает
Prisma-схему и Postgres-таблицу постоянного заказа (то, что происходит
ПОСЛЕ успешной оплаты), а Redis-холды остаются как есть — эфемерная
стадия ДО оплаты. Это будет ADR 0004 или правка этого документа.

## Отвергнутые варианты

**Postgres-таблица `SeatHold` с `expiresAt` + cron-очистка.** Работает,
но требует либо lazy-фильтрации по `expiresAt` на каждом чтении, либо
периодической джобы, которая физически удаляет протухшие строки — то,
что Redis TTL даёт бесплатно и без дополнительного кода.

**Общий с payment-сервисом Postgres-schema сразу.** Отклонено по той же
причине, что и просто добавление Postgres — форма таблицы заказа зависит
от деталей интеграции со Stripe, которых на этом этапе ещё нет.
