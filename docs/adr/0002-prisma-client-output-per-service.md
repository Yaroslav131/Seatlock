# ADR 0002. Свой output для Prisma Client в каждом сервисе

- **Статус:** принято
- **Дата:** 2026-09-05

## Контекст

При добавлении второго сервиса на Prisma (`catalog`, рядом с уже существующим
`auth`) оба используют одинаковую версию `@prisma/client`. pnpm в таком случае
физически связывает оба сервиса с **одним и тем же** местом в своём хранилище
(`node_modules/.pnpm/@prisma+client@X.Y.Z_.../node_modules/.prisma/client`) —
это подтверждено напрямую: `readlink` для `apps/auth/node_modules/@prisma/client`
и `apps/catalog/node_modules/@prisma/client` указывал на идентичный путь.

`prisma generate` пишет сгенерированный код (модели, типы) именно в это общее
место. Значит, чей `generate` выполнился последним — тот и остаётся, а другой
сервис молча получает чужую схему. Проверено на практике: после генерации для
`catalog` в общем хранилище не осталось моделей `auth` вообще, и наоборот.
Разница между сервисами обнаруживается только на `tsc`/рантайме, не раньше —
ни `pnpm install`, ни сам `prisma generate` об этом не предупреждают.

## Решение

Каждая `schema.prisma` получает свой уникальный `output`, генерирующий клиент
внутри `src/` самого сервиса, а не в общий `node_modules`:

```prisma
generator client {
  provider = "prisma-client-js"
  output   = "../src/generated/prisma"
}
```

Импорт — по относительному пути (`../generated/prisma`), а не `@prisma/client`.

## Последствия

- **`nest-cli.json`** у каждого сервиса получил `assets: [{ include:
"generated/**/*", outDir: "dist" }]` — иначе скомпилированный `dist/main.js`
  ищет клиента по пути `dist/generated/prisma`, а `nest build` копирует туда
  только `.ts`-файлы, не сгенерированный Prisma код. Без этого рантайм падает
  с "Cannot find module".
- **Docker.** Стадия сборки (`node:22-slim`, Debian) и стадия рантайма
  (`node:22-alpine`, musl) — разные ОС, и Prisma генерирует движок под
  конкретную ОС. `nest build` копирует `src/generated → dist/generated` только
  на стадии **сборки** (Debian), а рантайм-стадия своей `nest build` не вызывает
  вообще. Поэтому в `dist/generated`, приехавшем из стадии сборки, оказывается
  движок не под ту ОС. Фикс — отдельный `RUN` в рантайм-стадии Dockerfile,
  который **после** копирования `dist` из стадии сборки перезатирает
  `dist/generated` свежесгенерированным (на этой же, alpine-стадии) клиентом.
  Поймано и проверено вживую на `auth`: без этого шага контейнер стартовал и
  тут же падал с `PrismaClientInitializationError` про несовпадение движка.
- **`.dockerignore`** должен исключать `**/src/generated` — иначе Docker
  утаскивает в образ локально сгенерированный (под Windows/macOS) клиент поверх
  правильного, который сама сборка только что создала внутри контейнера.
- **`.gitignore`** и **ESLint** (`ignores`) — `src/generated` не коммитится и
  не проверяется линтером: это чужой сгенерированный код, а не наш.
- **`jest`** получил `modulePathIgnorePatterns: ["<rootDir>/dist"]` — иначе
  haste-map ругается на коллизию имён между копией в `src/generated` и той, что
  осталась в `dist/generated` от прошлой сборки.

## Отвергнутые варианты

**Не выносить `output` вообще, оставить дефолт.** Работало, пока сервис с
Prisma был один. Ломается молча при добавлении второго — самый неприятный тип
бага: ни один автоматический шаг (install, generate, даже `tsc` в отрыве от
реального запуска) не укажет на проблему явно, только рантайм-ошибка либо
(что хуже) тихо неверная схема без единой ошибки, если бы модели случайно
совпали по имени.
