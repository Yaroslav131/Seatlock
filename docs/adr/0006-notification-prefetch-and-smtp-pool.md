# ADR 0006. notification: параллельная обработка и пул SMTP-соединений; PDF остаётся в основном потоке

- **Статус:** принято
- **Дата:** 2026-09-21

## Контекст

План этапа 2 предполагал два шага: увеличить `prefetch` consumer'а (было жёстко `1`) и вынести
генерацию PDF в отдельный worker thread, чтобы она не блокировала event loop. Перед тем как
писать worker, замерили, из чего складывается обработка одного `order.paid` (dev-стек, Node 24):

| Шаг                                          | Время                                          |
| -------------------------------------------- | ---------------------------------------------- |
| генерация PDF (pdfkit + qrcode)              | ~8 мс медиана, 35 мс первый вызов              |
| 20 PDF параллельно                           | 136 мс всего, event loop блокировался до 46 мс |
| загрузка в MinIO                             | ~22 мс                                         |
| **отправка письма (SMTP, новое соединение)** | **~8 с** (Mailpit в Docker Desktop)            |
| отправка письма по уже открытому соединению  | 5–9 мс                                         |

Вывод: PDF стоит копейки. Дорого установление SMTP-соединения (TCP + TLS + AUTH): `nodemailer`
без пула открывает новое соединение на каждое письмо. 8 с в dev — артефакт окружения, но в проде
та же ошибка проявится как сотни миллисекунд на письмо (Resend по TLS), и при `prefetch=1` они
складываются последовательно: пропускная способность одного воркера ограничена `1 / задержка_SMTP`.

## Решение

1. **`NOTIFICATION_PREFETCH`** (по умолчанию `1`, в проде `3`) — сколько сообщений в работе
   одновременно. Значение проверяется на старте (целое от 1 до 50), опечатка — ошибка запуска, а не
   тихий откат к прежнему поведению. Параллельность безопасна благодаря атомарному захвату заказа
   (`claim()` в `order-paid.consumer.ts`): дубль сообщения или гонка двух обработчиков не приведут
   ко второму письму.
2. **Пул SMTP-соединений** (`pool: true`, `maxConnections = NOTIFICATION_PREFETCH`): соединения
   переиспользуются, пул закрывается при остановке сервиса.
3. **PDF остаётся в основном потоке.** Worker thread не даёт выигрыша: ~8 мс CPU на билет (при 11
   заказах/с это ~9% одного ядра), а на сервере всего 2 vCPU, которые и так делят все сервисы —
   работа переехала бы на другое ядро, но никуда бы не делась. Цена — компиляция отдельного
   worker-файла, запасной путь под ts-jest, сериализация буферов, отдельные ошибки потока. Вернуться
   к этому стоит, если PDF станет тяжёлым (картинки, шрифты, много страниц) или метрика lag
   event loop у notification начнёт расти.

## Почему `prefetch=3`, а не больше

Потолок задаёт почтовый релей: по документации Resend лимит по умолчанию — 10 запросов/с на
команду, при превышении ответ `429` (относится ли лимит к SMTP, документация прямо не говорит).
Три письма в работе при 200–500 мс на письмо — это теоретически 6–15 писем/с, то есть в самом
пике лимит достижим. На практике поток реальных оплат на порядки ниже (нагрузочный тест письма не
шлёт), а прежний `prefetch=1` при тех же задержках давал 2–5 писем/с. Если релей всё же отклонит
письмо, оно уйдёт в DLQ и его можно повторить (`docs/runbooks/notification-dlq.md`), письмо не
теряется. Поднимать значение стоит только вместе с повышением лимита у провайдера, а после выкатки
стоит посмотреть, растёт ли `order_paid_processed_total{result="failed"}`.

## Последствия

- Пропускная способность notification растёт примерно пропорционально `prefetch`, пока
  ограничением остаётся задержка SMTP/S3, а не CPU.
- При падении процесса вместо одного неподтверждённого сообщения вернутся до `prefetch` штук; аренда
  захвата (`CLAIM_LEASE_SECONDS`) по-прежнему защищает от дублей.
- Интеграционные тесты notification теперь идут при `prefetch=3`, отдельный тест проверяет, что
  отправки перекрываются во времени (при `prefetch=1` он падает).
