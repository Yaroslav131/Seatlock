# ADR 0001. PostgreSQL как основная база, MongoDB — точечно

- **Статус:** принято
- **Дата:** 2026-09-04

## Контекст

Проекту нужно хранить пользователей, события, схемы залов, брони, заказы и платежи.
Изначально рассматривались два варианта: MongoDB для всего или PostgreSQL для всего.

Главный инвариант системы: **одно место не может быть продано дважды**.
При распродаже популярного события сотни запросов одновременно борются
за один и тот же ряд кресел.

## Решение

Основная база — **PostgreSQL 17**. Схема на каждый сервис внутри одного инстанса,
отдельный пользователь БД на сервис, запрет на чтение чужой схемы через гранты.

**MongoDB** используется только в сервисе `notification` — для журнала отправок
и шаблонов писем.

## Причины

1. **Инвариант требует транзакций.** Переход места из `HELD` в `SOLD` вместе
   с созданием заказа — атомарная операция. В Postgres это одна транзакция
   плюс `SELECT ... FOR UPDATE`. В MongoDB пришлось бы городить это руками.

2. **Уникальные частичные индексы.** Правило «на одно место не больше одной
   активной брони» выражается одним индексом и обеспечивается базой,
   а не надеждой на корректность кода приложения.

3. **Деньги требуют ссылочной целостности.** Заказ без пользователя или
   платёж без заказа не должны быть выразимы в принципе.

4. **Данные жёстко реляционные.** Площадка → зал → секция → ряд → место →
   бронь → заказ → платёж. Это дерево внешних ключей, а не документы.

5. **MongoDB уместна в notification.** Логи отправок — документы разной формы,
   схема меняется, транзакции не нужны, объём растёт быстро. Здесь гибкость
   документной модели действительно помогает, а не мешает.

## Последствия

- Нужны миграции. Применяются **отдельным шагом деплоя**, а не при старте
  приложения — иначе несколько экземпляров сервиса начнут мигрировать
  одну базу одновременно.
- Схема на сервис, а не отдельный инстанс на сервис: логическая изоляция
  сохранена, а платить за шесть баз в AWS не приходится. Разнести физически
  можно позже без изменения кода.
- Два разных драйвера и два стиля работы с данными в одном проекте —
  осознанная цена за то, чтобы каждое хранилище решало свою задачу.

## Отвергнутые варианты

**MongoDB для всего.** Пришлось бы эмулировать транзакционную защиту
инварианта в коде приложения. Основная сложность проекта сместилась бы
с архитектуры на борьбу с базой.

**Отдельный инстанс Postgres на каждый сервис.** Канонический вариант
«database per service», но в AWS это шесть платных инстансов RDS вместо одного.
Для учебного проекта цена не оправдана, а изоляция схемами даёт
90% пользы за 0% стоимости.
